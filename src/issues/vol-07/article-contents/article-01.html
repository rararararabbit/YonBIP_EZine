编码开发规范

技能的git项目命名规范

各个领域使用各自的git仓库放置Skill代码，git项目命名使用“小写字母 + 连字符”。由“微服务编码 + -skills结尾”构成，例如：yonbip-hr-commonbe-skills。

git项目目录结构

技能项目目录包含一个或多个技能目录，单个技能的目录遵循章节“Skill基本规范”中“目录结构”的规范。

Skill的git项目目录结构示例：

skill-git-project-name/        # git项目目录名，由“微服务编码-skills”构成
├── skill-x-name/        # 技能目录
│ ├── SKILL.md       # 必选：元数据 + 操作说明
│ ├── scripts/          # 可选：可执行代码脚本
│ │   ├── merge_excel.py     # 主逻辑
│ │   └── utils.py     # 工具函数
│ ├── references/       # 可选：文档资料
│ ├── assets/           # 可选：模板、资源文件
│ └── ...               # 其它文件或目录，例如python脚本依赖requirements.txt
├── skill-y-name/        # 技能目录
│ ├── SKILL.md       # 必选：元数据 + 操作说明
│ ├── scripts/          # 可选：可执行代码
│ │   ├── search_staff.py     # 主逻辑
│ │   └── utils.py     # 工具函数
│ ├── references/       # 可选：文档资料
│ ├── assets/           # 可选：模板、资源文件
│ └── ...               # 其它文件或目录
├── ...
├── README.md
└── .gitignore

脚本代码开发规范

开发语言与依赖版本

脚本代码使用python语言开发，python版本要求3.12及以上。

脚本命名规范

python脚本命名应遵守PEP 8 官方规范。主要内容摘录见下表。

附表《PEP 8 官方规范主要内容》：

代码对象命名风格示例说明
模块/文件小写+下划线merge_excel.py
image_editor.py		文件名应简短且具有描述性。
包/目录全小写skills/
scripts/
utils/		目录名尽量不使用下划线，但在 Skill 结构中为了可读性有时也会使用。
类名大驼峰TaskManager
UserProfile		类名首字母大写，不使用下划线。
函数/方法小写+下划线create_user()
get_task_info()		动词开头，清晰表达功能。
常量UPPER_CASEMAX_RETRIES
API_KEY		全大写，单词间用下划线分隔。

对于主入口python脚本，其文件名称应使用全小写+下划线（注意此处与技能命名的差异）。推荐文件名以动宾形式或名词短语命名，为AI理解提供便利，例如merge_excel.py。动宾形式强调做什么（功能/行为），名词短语强调是什么（实体/工具）。

调用BIP接口

统一使用公共函数包yonbip-skill-utils中的requests调用BIP接口。（python环境需先安装工具包，安装执行命令：pip install --upgrade yonbip-skill-utils）

代码示例：

yonbip_requests对接了BIP的会话token统一管理机制，技能开发人员编写Skill脚本时使用此公共函数包无需自己处理友户通会话token。

from yonbip_skill_utils import requests as yonbip_requests

def run():
  res=yonbip_requests.post(skill_info={},url,data) # post请求示例
# res=yonbip_requests.get(skill_info={},url) # get请求示例
  …

函数参数说明：

■ skill_info：传技能信息{"name":"...","version":"..."}。

■ url：调用接口的相对路径，即不需要http/https、域名和端口号。

■ python标准requests包中post、get函数支持的参数，该公共函数包同样支持。

日志输出

使用公共函数包 yonbip_skill_utils的logging输出日志，用于统一日志输出，便于日志采集和分析。

代码示例：

from yonbip_skill_utils import logging

logger = logging.get_package_logger("技能name")

logger.info("...")

脚本输出返回值

脚本返回值必须使用print()方法输出，输出内容为JSON结果。

代码示例：print(json.dumps(result, ensure_ascii=False, indent=2))

返回值的JSON格式为：

{

"success": True/False,

"message": "..",

"data": {},

...

}

必须的键值为：success、message。

值的类型要求：

■ success的值必须是布尔型。

■ message的值必须是字符串。

■ data的值必须是JSON对象。

返回值示例：

成功
{
  "success": True,
  "message": "成功信息",
  "data": { "key": "结果" }
}

# 错误
{
  "success": False,
  "message": "错误原因",
  "data": None
}

为了方便输出统一的错误信息，公共函数包yonbip_skill_utils在tools中提供了print_fail()函数。使用示例：

from yonbip_skill_utils import tools

tools.print_fail("参数 name 不能为空。")

错误处理规范

一、调用BIP接口异常或错误：公共函数yonbip_requests仅打印异常错误日志，不会处理http异常状态码、BIP接口内部错误码。领域代码应按业务需求处理http异常状态码、BIP接口内部错误码。

二、领域技能脚本代码内部的异常或错误：

1、细分异常捕获：避免使用“BaseException”捕获所有异常，应根据具体场景捕获特定异常。捕获异常代码示例：

try:
    # 业务逻辑
    pass

# 1. 空值/类型错误
except (TypeError, AttributeError, KeyError) as e:
    yonbip_logger.error(f"[Skill] 数据异常: {errorCode},{e}")
    return ...

# 2. 数值/计算错误
except (ValueError, ZeroDivisionError) as e:
    yonbip_logger.error(f"[Skill] 计算异常: {e}")
    return ...

# 3. 如果调用OpenClaw的库，则需要捕获OpenClaw特有异常，例如ConfigurationError
#except ConfigurationError as e:  # 假设引擎定义的API异常
#    yonbip_logger.error(f"[Skill] 引擎接口调用失败: {errorCode}, {e}")
#    return ...

# 4. 兜底其它未知异常
except Exception as e:
    yonbip_logger.error(f"[Skill] 未知致命错误: {errorCode},{e}")
    return ...

2、禁止将异常直接抛出，需将错误信息转换为标准化输出。

三、异常信息需详细、明确，包含错误原因、影响范围，便于排查问题（禁止返回“执行失败”等模糊信息）。

四、基于BIP异常码规范使用异常码，便于识别错误类型进行后续处理，以及ymc分析。

脚本参数规范

脚本输入参数统一使用双横线长参数格式。示例：“python scripts/query_staff_list.py --name "张三" --page-index 1”。示例中“--name”即为双横线长参数。

长参数命名规则如下：

■ 参数名仅可使用小写字母、数字和短横线 -

■ 参数名必须以小写字母开头

■ 参数名长度建议为 2 ~ 30 个字符

■ 参数名与参数值之间必须使用空格分隔

参数传递格式如下：

■ 参数名前必须使用双横线 --。

■ 参数名与参数值之间必须使用空格分隔。

■ 禁止使用短参数或位置参数。

对LLM不可信输入源做强制校验

大模型调用BIP接口的参数属于不可信输入源，需严格校验过滤，防止非法参数引发数据异常，或触发非预期的海量数据查询、更新操作引发服务不可用风险。

控制措施如下：

■ 技能脚本参数校验要求：要求对所有入参执行强制性校验。校验范围涵盖：参数类型、长度限制、数值区间、空值校验、特殊字符过滤以及业务逻辑合法性校验。同时对数据查询、更新操作需限定最大处理条数，防止非预期的大规模数据操作。

■ 后端参数校验要求：面向技能开放的OpenAPI需同步增加参数合理性校验，构建技能脚本、OpenAPI双重校验防护机制。

脚本注释不能替代SKILL.md规则

不要期望LLM在业务执行时通过读取脚本注释、参数映射来调整自身行为。

通常情况下，LLM 主要依据SKILL.md中的规则执行任务，只负责按规定参数调用脚本并解析脚本返回结果，不会主动读取脚本源码。

因此，如果希望约束模型行为，应写在SKILL.md中，而不是依赖脚本注释。

脚本注释主要面向脚本维护者，适合说明脚本职责、关键函数、字段处理逻辑和维护注意事项。
