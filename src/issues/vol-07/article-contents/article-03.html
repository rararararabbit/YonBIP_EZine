【强制】必须设置正确的 HTTP 响应 Content-Type，禁止错误类型导致解析风险

1、 核心定义与风险说明

●风险定义：Content-Type 用于告诉浏览器响应数据的格式。若配置错误（如接口返回 JSON/文本却设置为 text/html），浏览器会错误解析非 HTML 内容为 HTML/JS，攻击者可构造恶意内容触发反射型 XSS、文件解析异常、数据泄露；

●核心危害：非 HTML 响应被错误当作 HTML 解析，会大幅提升 XSS 漏洞利用成功率，导致恶意脚本在用户浏览器执行。

2、 核心安全规则

●强制正确匹配

响应数据格式必须与 Content-Type 严格一致：

1) JSON 接口 → application/json; charset=UTF-8

2) 纯文本 → text/plain; charset=UTF-8

3) XML 数据 → application/xml; charset=UTF-8

4) 文件下载 → application/octet-stream 或对应文件类型

5) 图片/音视频 → 对应媒体类型（image/png、image/jpeg 等）

●强制携带编码

所有文本类响应必须指定 charset=UTF-8，防止乱码与解析异常。

3、 禁止/不推荐的行为

✗禁止非 HTML 响应使用 text/html（接口、文本、XML、JSON 均不允许）；

✗禁止省略 Content-Type，依赖浏览器自动猜测（MIME Sniffing）；

✗禁止统一使用 text/html 适配所有接口。

4、 增强安全配置（推荐）

●增加 X-Content-Type-Options: nosniff 响应头，强制浏览器严格遵守 Content-Type，禁止自动猜测数据类型，从根本上阻断 MIME 类型嗅探触发的 XSS；

●静态资源（图片/JS/CSS）必须配置正确的资源类型；

●所有接口统一配置安全响应头，避免遗漏。

【强制】统一配置安全 HTTP 响应头，防范 XSS、点击劫持、MIME 嗅探、Cookie 劫持

1、 核心定义与风险说明

●风险背景：缺失安全响应头会导致浏览器缺乏安全约束，容易遭受点击劫持、XSS、Cookie 窃取、MIME 嗅探、非法跨域等攻击；

●防护目标：通过服务端统一配置安全响应头，为浏览器提供强制安全策略，大幅降低前端攻击面。

2、 安全响应头配置规范

响应头推荐值作用与安全说明
X-Content-Type-Optionsnosniff禁止浏览器 MIME 嗅探，必须严格按照 Content-Type 解析，防止非 HTML 内容被解析为 HTML 触发 XSS
X-Frame-OptionsDENY 或 SAMEORIGIN防范点击劫持，禁止页面被嵌套 iframe/frame/embed
Set-CookieHttpOnly; Secure; SameSite=Strict防止 XSS 窃取 Cookie、防止 HTTPS 明文传输、防止 CSRF 跨站携带
Strict-Transport-Securitymax-age=31536000; includeSubDomains强制 HTTPS，防止 HTTP 降级劫持（HSTS）
Access-Control-Allow-Origin精确域名（白名单）禁止设置为 *，必须使用动态白名单匹配合法来源
Content-Security-Policydefault-src 'self'防 XSS、防资源注入，限制脚本/图片/样式加载源
X-XSS-Protection1; mode=block启用浏览器 XSS 过滤器，强制阻断检测到的 XSS

3、 核心安全规则

●Cookie 安全三要素（强制）

1) HttpOnly=true：禁止 JS 读取 Cookie，彻底防范 XSS 窃取会话；

2) Secure=true：仅在 HTTPS 下传输 Cookie，防止 HTTP 明文截获；

3) SameSite=Strict/Lax：禁止第三方跨站请求携带 Cookie，强力防御 CSRF。

●跨域访问（CORS）强制规则

1) 禁止使用 * 作为跨域允许来源；

2) 必须从请求头获取 Origin 并与预定义白名单匹配；

3) 仅允许业务必需的域名跨域。

●点击劫持防护

1) 无嵌套需求：使用 DENY；

2) 需同源嵌套：使用 SAMEORIGIN；

3) 禁止随意使用 ALLOW-FROM（已废弃，兼容性差）。

●全局统一配置

所有接口、页面必须统一自动注入安全响应头，禁止每个接口单独配置。

4、 禁止/不推荐的行为

✗禁止跨域配置 Access-Control-Allow-Origin: *；

✗禁止登录 Cookie 不设置 HttpOnly/Secure；

✗禁止缺失 X-Content-Type-Options: nosniff；

✗禁止使用已废弃的 ALLOW-FROM；

✗禁止在 HTTP 环境下传输敏感 Cookie。

【强制】对输出信息校验，避免信息泄露

1、 核心定义与风险说明

●风险定义：服务端直接向客户端（浏览器/接口调用方）返回系统原生异常堆栈、SQL 语句、文件路径、服务器版本、配置信息、代码行数等敏感内容，攻击者可通过这些信息进行SQL 注入、目录遍历、未授权访问、服务器版本漏洞利用；

●防护目标：所有对外输出内容必须经过安全过滤，异常信息仅在服务端日志留存，绝不返回给客户端。

2、 禁止泄露的敏感信息

●异常堆栈信息（StackTrace）、异常完整类名、代码行号

●数据库类型、版本、账号、表结构、SQL 语句、连接信息

●服务器中间件版本（Tomcat、Nginx、Java 版本）

●操作系统类型、版本、内核信息

●服务器文件路径、绝对路径、目录结构

●业务配置信息、密钥、账号、内部接口地址

●未脱敏的用户隐私数据（身份证、手机号、密码）

3、 核心安全规则

●异常统一封装

1) 所有异常必须被全局捕获并友好封装，仅返回业务错误码 + 简短提示（如 “系统繁忙，请稍后再试”）；

2) 禁止使用 printStackTrace()、response.getWriter().write(exception) 直接输出异常。

●自定义错误页面

1) Web 项目必须配置全局统一错误页（404/500），禁止展示服务器默认错误页；

2) RESTful API 必须返回标准化、无敏感信息的 JSON 结构。

●日志与输出分离

1) 详细异常、堆栈、SQL、路径信息仅记录在服务端日志，供运维排查；

2) 客户端只获取业务提示，无法看到任何系统内部细节。

●敏感数据脱敏

1) 必须输出的用户数据必须脱敏（手机号、身份证、邮箱、银行卡）。

4、 禁止/不推荐的行为

✗禁止在 catch 块中将异常直接返回给前端；

✗禁止使用 Tomcat/Jetty 默认错误页面；

✗禁止在接口响应中返回 Exception.getMessage() 原始信息；

✗禁止在日志外泄露 SQL、路径、版本信息；

✗禁止开发环境与生产环境使用同一套异常输出策略。

错误示例：直接输出异常与堆栈，导致严重信息泄露

try {
// 数据库操作
} catch (SQLException e) {
// 严重违规：直接返回堆栈、SQL、数据库信息
e.printStackTrace();
response.getWriter().write("异常：" + e.toString());
}

import java.util.regex.Pattern;
public class SecureExceptionStandardizationTool {
/**
* 敏感信息黑名单正则（匹配堆栈轨迹、类全路径、常见底层异常等）
* 例如: "at com.yonyou...", "java.lang.NullPointerException", "SQLException..."
*/
private static final Pattern SENSITIVE_INFO_PATTERN = Pattern.compile(
"(?i)(at\\s+\\w+\\.|\\.java:\\d+|Exception|Error|Caused by|null|SQLException|ClassNotFoundException)",
Pattern.CASE_INSENSITIVE
);

/**
* 安全的异常转换方法
* @param bizCode 业务错误码
* @param defaultSafeMsg 国际化后的安全默认提示 (如 "参数解析失败")
* @param e 异常对象 (仅用于日志记录，不直接拼接到返回值)
* @return
*/
public static JsonResponse transStdException(String bizCode, String defaultSafeMsg, Exception e) {
// 1. 获取异常原始信息
String rawMessage = (e != null) ? e.getMessage() : "";

// 2. 安全校验：如果原始信息为空，或者命中了敏感特征，强制使用默认安全提示
if (rawMessage == null || rawMessage.trim().isEmpty() || SENSITIVE_INFO_PATTERN.matcher(rawMessage).find()) {
return new JsonResponse().failed(bizCode, defaultSafeMsg);
}

// 3. 长度限制：防止超长异常信息撑爆前端日志或进行缓冲区攻击
if (rawMessage.length() > 200) {
rawMessage = rawMessage.substring(0, 200) + "...";
}

// 4. 如果未命中黑名单且长度正常，可以认为是业务主动抛出的安全提示（如 "用户名已存在"），允许透传
return new JsonResponse().failed(bizCode, rawMessage);
}

/**
* 专门用于处理参数绑定异常的安全提取（提取字段名是安全的，提取类名是不安全的）
*/
public static String extractSafeBindErrorMsg(BindException e) {
StringBuilder safeMsg = new StringBuilder("参数校验失败: ");
e.getBindingResult().getFieldErrors().forEach(error -> {
// 只暴露字段名和校验规则（如：name不能为空），绝对不暴露 error.toString()
safeMsg.append(error.getField()).append(error.getDefaultMessage()).append("; ");
});
return safeMsg.toString();
}
}

【建议】接口返回数据遵循最小化原则，禁止返回多余敏感字段

1、 核心定义与风险说明

●风险定义：接口返回多余字段、非业务必需字段、敏感隐私字段，会导致用户隐私泄露、业务数据泄露、权限信息泄露、越权利用；

●防护目标：严格遵循最小权限原则，前端需要什么就返回什么，禁止全量返回实体对象。

2、 核心安全规则

●必须按需返回

接口返回数据必须严格按照前端业务需求定义返回字段，禁止直接返回数据库实体对象（DO/POJO）、禁止全字段返回。

●敏感信息必须剔除/脱敏

以下信息严禁直接明文返回，必须剔除或脱敏：

1) 密码、加密密钥、盐值、Token 密钥

2) 身份证号、手机号、邮箱、地址、银行卡

3) 内部主键、用户盐值、权限标识、内部状态

4) 业务核心数据、成本、底价、策略配置

●必须使用数据传输对象（DTO/VO）隔离

禁止将数据库实体直接序列化为 JSON 返回前端，必须使用VO/DTO 做数据隔离，手动选择需要返回的字段。

●列表接口禁止返回冗余详情

列表页仅返回简单展示字段，详情页再返回完整信息，避免大数据量、敏感字段在列表泄露。

3、 禁止/不推荐的行为

✗禁止直接使用 mybatis-plus、jpa 等框架直接返回实体对象给前端；

✗禁止为了方便，一次性返回所有用户/业务字段；

✗禁止返回密码、加密盐、密钥、内部 ID 等敏感字段；

✗禁止列表接口返回大字段、附件、日志等冗余数据。

/**
* 处理用户出站数据的加密与脱敏配置
*/
private void processUserEncryptConfig(JSONObject jsonObject, boolean isTransform, final String sysId, final String md5SecretKey, final boolean isAes, final boolean isCipher) {
if (jsonObject == null) {
return;
}

// ==========================================
// 第一步：最小化原则 - 物理剔除绝对不可外传的敏感凭证字段
// ==========================================
Iterator<String> iterator = jsonObject.keys();
while (iterator.hasNext()) {
String key = iterator.next();
if (getUnTransportPropertySet().contains(key)) {
iterator.remove(); // 移除密码、盐值、密钥等高危字段
}
}

// 专属云环境跳过后续的加解密处理
if (YhtExclusiveCloudUtils.isExclusiveCloud()) {
return;
}

// 如果未开启转换标识，直接返回（保留脱敏后的基础数据）
if (!isTransform) {
return;
}

// ==========================================
// 第二步：判断下游系统是否具备密钥解密能力
// ==========================================
boolean decodeContact = false;
String plainSecretKey = secretKeyService.getPlainSecretKey(sysId, md5SecretKey);
if (StringUtils.isNotBlank(plainSecretKey)) {
decodeContact = true;
}
boolean finalDecodeContact = decodeContact;
boolean isPHPSecretKey = secretKeyService.isPHPSecretKey(plainSecretKey);

// ==========================================
// 第三步：针对特定 PII 字段（手机号、邮箱）进行脱敏或重加密
// ==========================================
Iterator<String> newIterator = jsonObject.keys();
while (newIterator.hasNext()) {
String key = newIterator.next();
Object obj = jsonObject.get(key);

// 处理手机号
if (TenantUser.USERMOBILE.equalsIgnoreCase(key)) {
if (obj == null) {
continue;
}

String mobile = (String) obj;
mobile = UserUtil.decryptContact(mobile); // 先将内部加密格式解密为明文

if (StringUtils.isNotBlank(mobile) && finalDecodeContact) {
if (!isCipher) {
continue;
}
// 下游有密钥且要求密文传输：使用指定算法重新加密
jsonObject.put(key, encryptString(plainSecretKey, mobile, isAes, isPHPSecretKey));
} else {
// 下游无密钥或不要求密文：进行掩码脱敏处理 (如 138****1234)
jsonObject.put(key, UserUtil.getUserPhone(mobile));
}
}

// 处理邮箱
if (TenantUser.USEREMAIL.equalsIgnoreCase(key)) {
if (obj == null) {
continue;
}

String email = (String) obj;
email = UserUtil.decryptContact(email); // 解密为明文

if (StringUtils.isNotBlank(email) && finalDecodeContact) {
if (!isCipher) {
continue;
}
// 重加密
jsonObject.put(key, encryptString(plainSecretKey, email, isAes, isPHPSecretKey));
} else {
// 掩码脱敏 (如 t***t@domain.com)
jsonObject.put(key, UserUtil.getUserEmail(email));
}
}
}
}
